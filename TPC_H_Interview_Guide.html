What is TPC-H?

Interviewers love this because it tests whether you know why the benchmark exists, not just that you ran SQL.

Definition

TPC-H (Transaction Processing Performance Council – H) is an industry-standard decision-support / OLAP benchmark. It models a wholesale supplier business and measures how well a database answers complex analytical queries.

What it includes

  • Fixed schema: 8 tables
  • Synthetic data generator (dbgen)
  • 22 official SQL queries (ad-hoc / reporting style)
  • Scale Factor (SF) to grow data size
  • Metrics like query latency / power / throughput (full official runs)

What my project measured

I focused on a practical subset: generate data → load two engines → time Q1–Q22 and compare DuckDB vs PostgreSQL latency. Not a full audited TPC publication run — an engineering comparison study.

TPC-H vs TPC-C (bonus)

  • TPC-C: OLTP — many short transactions
  • TPC-H: OLAP — fewer, heavy analytical queries with joins/aggregations
Q: Why use TPC-H instead of random SQL queries?
TPC-H is a standard, well-known workload. Results are comparable across systems, queries stress joins, filters, aggregations and large scans, and interviewers/recruiters recognize it. Random queries wouldn’t prove much about analytical performance.
Q: Is your result an official TPC-H score?
No. Official TPC results have strict audit rules, pricing metrics, and run methodology. My project is a controlled latency comparison of two engines on TPC-H queries/data at SF=5 in Colab — useful for learning and engineering insight, not a published TPC metric.

Full Workflow — Step by Step

This is the complete explanation of what the notebook does, in interview language. If they say “walk me through the workflow,” use this section.

STEP 01
Environment setup (Colab)

Install Python packages (duckdb, pandas, psycopg2-binary) and system PostgreSQL via apt-get. Start the Postgres service and create a database. This gives one notebook both an embedded OLAP engine and a classic RDBMS.

↓
STEP 02
Generate TPC-H data in DuckDB

INSTALL tpch; LOAD tpch; then CALL dbgen(sf=5). DuckDB’s built-in generator creates all 8 TPC-H tables at scale factor 5 (~5 GB). No separate C dbgen binary needed.

↓
STEP 03
Validate generated tables

SHOW TABLES, sample rows with LIMIT, and check counts (e.g. orders). Confirms generation succeeded before the expensive transfer to PostgreSQL.

↓
STEP 04
Create PostgreSQL schema (DDL)

Connect with psycopg2 and CREATE TABLE for region, nation, supplier, customer, part, partsupp, orders, lineitem — matching TPC-H column types (INTEGER, DOUBLE PRECISION, DATE, TEXT, CHAR).

↓
STEP 05
Export DuckDB → CSV → load PostgreSQL

For each table: DuckDB COPY table TO 'table.csv', then PostgreSQL COPY … FROM STDIN WITH CSV HEADER via copy_expert. Bulk load is mandatory at SF=5; row inserts would be too slow.

↓
STEP 06
Row-count validation

Run SELECT COUNT(*) on every PG table. Especially check fixed dimensions: region = 5, nation = 25. Truncate/reload if a re-run duplicated small tables.

↓
STEP 07
Load official TPC-H queries (Q1–Q22)

Pull SQL from DuckDB tpch_queries() (also downloaded tpch-kit SQL files). Normalize reserved word: replace orders with "orders" for PostgreSQL compatibility.

↓
STEP 08
Index + ANALYZE (PostgreSQL tuning baseline)

Create B-Tree indexes on join keys (l_orderkey, o_orderkey, o_custkey, c_custkey, s_suppkey, n_nationkey). Run ANALYZE so the planner has fresh statistics. Set statement_timeout = 300000 (5 min).

↓
STEP 09
Benchmark loop

For each query: time DuckDB execution; time PostgreSQL execution; on PG failure/timeout → store TIMEOUT and ROLLBACK so the connection stays usable. Print per-query latencies.

↓
STEP 10
Interpret results

Compare engines: DuckDB typically seconds; PostgreSQL tens of seconds to minutes (or timeout). Explain via columnar OLAP vs row-store RDBMS architecture — not “Postgres is bad,” but “wrong tool shape for pure analytics without deep tuning.”

Q: Why DuckDB for generation instead of the original TPC dbgen tool?
DuckDB’s INSTALL tpch; CALL dbgen(sf=N) generates the full schema in one call inside the notebook — no separate C tool chain. Perfect for Colab reproducibility. The data follows TPC-H scale rules.
Q: Why compare DuckDB and PostgreSQL specifically?
They represent two design philosophies: DuckDB = embedded columnar OLAP, PostgreSQL = general-purpose row-oriented RDBMS. Same SQL workload on both makes the architectural difference visible in latency numbers.
Q: Why CSV and not INSERT statements?
At SF=5, lineitem alone is huge. Row-by-row inserts would take forever. COPY / bulk load is the standard high-throughput path in PostgreSQL.
Q: Why Google Colab?
I needed a machine with enough disk/RAM to hold ~5 GB generated data plus PostgreSQL, without local setup pain. Colab gives a ready Linux environment where I can apt-get install postgresql and run the full notebook.

Q: Which table is usually the bottleneck?
lineitem — it is the largest fact-like table. Most heavy TPC-H queries scan/join it. If lineitem is slow, the whole benchmark is slow.
Q: Why quote "orders" in PostgreSQL?
orders can conflict with SQL reserved/keyword usage depending on context. Quoting as "orders" forces PostgreSQL to treat it as an identifier. DuckDB was more forgiving; PG needed the quotes — so I quote only a bare orders word. A second pass leaves "orders" alone.

Q: What happens to row counts when SF increases?
Fact-like tables (lineitem, orders, customer, supplier, part, partsupp) grow roughly linearly with SF. Small dimensions (region=5, nation=25) stay fixed.
Q: Why SF=5 and not SF=1?
SF=1 is too small to show meaningful performance gaps on modern machines. SF=5 stresses joins/scans enough to expose DuckDB vs PostgreSQL differences while still fitting in Colab for a student project.
Q: Your resume mentions SF 1 to 50 — reconcile that.
I evaluated scalability across scale factors; the main notebook run documented in detail uses SF=5 as a practical Colab default. Larger SFs (10–50) increase generation/load/query time and can hit Colab memory/disk limits.

DuckDB vs PostgreSQL — How to Explain Results

Don’t just say “DuckDB was faster.” Explain why the architecture causes that.

AspectDuckDBPostgreSQL
Primary designEmbedded OLAP / analyticsGeneral-purpose RDBMS (OLTP + general SQL)
Storage styleColumnar (great for aggregates/scans)Row-oriented (great for point lookups / transactions)
ExecutionVectorized execution, tight in-processClassic volcano-style executor; client/server process
TPC-H fitExcellent — large scans, joins, GROUP BYsCan do it, but needs tuning/indexes; heavier for pure analytics
My observed trendSeconds (often <5s)Tens of seconds to minutes; some TIMEOUT / very slow (e.g. Q9)
Fairness caveat (say this in interview): PostgreSQL was running in Colab with basic indexes I created — not a fully tuned warehouse setup (no partitioning, limited memory tuning, no columnar extension). DuckDB is purpose-built for this workload. The comparison shows architectural tendency, not that “PostgreSQL is bad.”
Q: Why was DuckDB faster on TPC-H?
TPC-H queries mostly do large scans, multi-way joins, and aggregations. Columnar storage reads only needed columns; vectorized execution processes batches efficiently; DuckDB runs in-process with less client/server overhead. PostgreSQL’s row store is optimized more for transactional access patterns.
Q: Does that mean PostgreSQL shouldn’t be used for analytics?
No. PostgreSQL is excellent as a system of record, mixed workloads, and with tuning/extensions (indexes, partitioning, parallel query, or columnar add-ons). For pure heavy analytics at scale, specialized OLAP engines (DuckDB, ClickHouse, BigQuery, etc.) often win.

SQL / Implementation Deep Dive

Questions about what you actually coded in the notebook.

Bulk loading with COPY

# Fast path used in notebook with open(f"{table}.csv","r") as f: pg_cur.copy_expert( f"COPY {table} FROM STDIN WITH CSV HEADER", f ) pg_con.commit()
Q: What is COPY and why is it fast?
COPY is PostgreSQL’s bulk load/export command. It bypasses per-row INSERT overhead and parses CSV in a streaming fashion — orders of magnitude faster for millions of rows.

Indexing strategy

CREATE INDEX idx_lineitem_orderkey ON lineitem(l_orderkey); CREATE INDEX idx_orders_orderkey ON "orders"(o_orderkey); CREATE INDEX idx_orders_custkey ON "orders"(o_custkey); CREATE INDEX idx_customer_custkey ON customer(c_custkey); CREATE INDEX idx_supplier_suppkey ON supplier(s_suppkey); CREATE INDEX idx_nation_nationkey ON nation(n_nationkey); ANALYZE; -- refresh planner statistics
Q: Why these indexes?
They target common join keys in TPC-H (orderkey, custkey, suppkey, nationkey). Without them, PostgreSQL may hash/nest-loop scan huge tables repeatedly. Indexes help some queries; they don’t turn PG into a columnar engine.
Q: What does ANALYZE do?
ANALYZE collects table statistics (row counts, value distributions) so the query planner can choose better join orders and strategies. Stale stats → bad plans → slow queries.
Q: Can indexes make things slower?
Yes for writes (maintenance cost), and sometimes the planner picks a bad index nested-loop when a sequential scan + hash join would be better. For read-mostly benchmarks after load, indexes are usually helpful — but not magic.

Timeouts & timing loop

SET statement_timeout = 300000; -- 5 minutes (ms) for name, query in queries.items(): # DuckDB timed # PostgreSQL timed; on exception → "TIMEOUT" + rollback
Q: Why set statement_timeout?
Some PostgreSQL plans on SF=5 can run extremely long. A timeout keeps the benchmark from hanging forever and marks the query as TIMEOUT so I can still report results for the rest.
Q: Why rollback after timeout/error?
In psycopg2/PostgreSQL, a failed statement aborts the current transaction. You must ROLLBACK before the connection can run more SQL.

Challenges & How You Handled Them

Interviewers love STAR stories from real friction in the notebook.

Q: Tell me a challenge you faced in this project.
Challenge: PostgreSQL queries were extremely slow / timing out on SF=5. Action: Added join-key indexes, ran ANALYZE, set a 5-minute statement_timeout, and rolled back failed transactions so the loop could continue. Result: Could complete a comparative report instead of hanging; also clarified that engine architecture matters more than micro-optimizations alone.
Q: Any data loading issues?
Yes — for small dimension tables, accidental re-runs could inflate counts (region should be 5, nation 25). I added validation COUNT(*) checks and truncate/reload cells to fix bad loads.
Q: SQL portability issue?
Official queries needed "orders" quoting for PostgreSQL. A naive replace later broke DuckDB on Q13. Lesson: keep per-engine SQL or a careful rewriter, and test each dialect.
Q: Resource constraints?
Colab free tier has disk/RAM limits. SF=5 is a sweet spot; SF=10–50 can fail or become impractical without a larger machine. I chose SF based on environment constraints while still getting meaningful gaps.

DBMS Theory Questions They May Ask

Your project is a gateway into classic database interview topics. Be ready.

Q: OLTP vs OLAP?
OLTP: many short read/write transactions (orders, payments). OLAP: heavy analytical queries over historical data (TPC-H). PostgreSQL is often OLTP-first; DuckDB is OLAP-first.
Q: Row store vs column store?
Row store: stores all columns of a row together — great when you need whole rows. Column store: stores each column together — great when queries touch few columns over many rows (aggregations). TPC-H favors columnar.
Q: What is a query planner / optimizer?
The component that chooses how to execute SQL (join order, hash vs merge vs nested loop, use index or seq scan) based on statistics and cost models. Bad stats → bad plans → slow queries (why ANALYZE matters).
Q: Hash join vs nested loop vs merge join?
Nested loop: for each outer row, find matches (good if inner is indexed & small). Hash join: build hash table on one side — great for large equijoins. Merge join: both sides sorted on join key. TPC-H large joins often want hash joins.
Q: What is cardinality?
Estimated number of rows produced by an operator. Wrong cardinality estimates cause the optimizer to pick terrible plans — common root cause of “this query is mysteriously slow.”
Q: Primary key / foreign key — did you enforce them?
In the notebook schema I created tables with columns matching TPC-H, focused on load + benchmark speed. Strict PK/FK constraints can slow bulk load; in a production schema I’d add them for integrity after/during controlled loads. Be honest: this project prioritized benchmarking throughput over full constraint enforcement.
Q: What is EXPLAIN / EXPLAIN ANALYZE?
EXPLAIN shows the planned query tree. EXPLAIN ANALYZE actually runs it and shows real timings/row counts. I’d use this next to debug slow PostgreSQL queries (e.g. Q2, Q9).
Q: ACID — does it matter for TPC-H?
TPC-H is mostly read/analytical. ACID matters more for OLTP. Still, PostgreSQL’s MVCC/transaction model has overhead characteristics different from DuckDB’s analytical execution engine.
Q: What indexes exist? B-Tree vs Hash vs Bitmap?
PostgreSQL default is B-Tree (what I created). Hash indexes for equality; BRIN for huge append-only tables; bitmap scans appear in plans when combining conditions. For join keys, B-Tree is the standard choice.
Q: Normalization — is TPC-H normalized?
TPC-H is a mostly normalized schema (separate nation/region/customer/orders/lineitem). Analytical systems sometimes denormalize for speed; TPC-H deliberately stresses joins.

Quick-Hit Definitions

Q: What is TPC?
Transaction Processing Performance Council — standards body for database benchmarks (TPC-C, TPC-H, TPC-DS, etc.).
Q: What is dbgen?
The TPC-H data generator. In my project, invoked via DuckDB: CALL dbgen(sf=N).
Q: What is a scale factor?
Multiplier for dataset size. SF≈GB of raw data for TPC-H (SF1 ≈ 1GB).
Q: What is wall-clock latency?
End-to-end elapsed time from starting the query to receiving all results — what my timing loop measured with time.time().
Q: What is cold vs warm cache?
Cold: data read from disk. Warm: data already in memory. Warm runs look faster; fair benchmarks disclose which.
Q: What is vectorized execution?
Process columns in batches (vectors) instead of one row at a time — better CPU cache usage; used by DuckDB-like engines.
